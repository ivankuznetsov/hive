## Round 1
### Q1. Who is the primary actor for v0.1.0, and what is the expected normal operating flow from configuration through scheduled invocation to Telegram delivery?
### A1.
The primary actor is a self-hosting operator running PRDigest on a small VPS. They install the gem or image, provide an explicit repository list and timezone in YAML, provide GitHub and Telegram tokens through environment variables, configure one allowlisted Telegram chat, and enable the supplied systemd timer. Each timer invocation runs a oneshot `prdigest run`, computes owed local days from state, processes them oldest-first, fetches merged PRs, renders deterministic Telegram HTML, sends all chunks for one day, then atomically advances state before moving to the next day. Failures are visible through a non-zero exit and journald; the next timer run catches up from durable state.

### Q2. Which outcomes make an owed day “settled” and therefore eligible for immediate state advancement: successful delivery of every chunk, an empty-day message, dry-run rendering, or any other case?
### A2.
A day is settled after every rendered chunk is delivered successfully; after the configured empty-day message is delivered when `send_empty: true`; after an empty day is intentionally suppressed when `send_empty: false`; or when an over-cap historical day is explicitly skipped by catch-up policy and recorded as skipped. Dry-run never reads or writes delivery progress and never advances state. Any GitHub, rendering, Telegram, or state-write failure leaves the current day unsettled.

### Q3. If a digest is split into multiple Telegram messages and an early chunk succeeds but a later chunk fails, should the day remain wholly unadvanced and all chunks be resent on retry, accepting possible duplicates?
### A3.
Yes. The day remains wholly unadvanced until every chunk succeeds. A retry resends all chunks and may duplicate earlier chunks. This at-least-once behavior is accepted for v0.1.0 because avoiding duplicates would require a durable per-chunk delivery ledger; silent loss is worse than an occasional duplicate.

### Q4. When the backlog exceeds the configured catch-up cap, should each run process the oldest capped set and leave newer days owed, and what default and maximum cap should v0.1.0 enforce?
### A4.
No: process the newest capped window so a long outage does not permanently delay current reporting. Days older than that window are explicitly reported as skipped, and state advances past them before the retained days are processed oldest-first. Use a default cap of 7 days and a hard maximum of 30 days; reject values outside `1..30` as configuration errors.

### Q5. For the explicit date override, should a successful real send bypass state both for reading and writing, and should the command permit sending a date that was already delivered?
### A5.
Yes. `--date YYYY-MM-DD` is an explicit operator replay: it bypasses state for both scheduling and persistence, permits resending an already delivered date, and never changes `last_digested_date`. The JSON result must identify the run as an explicit-date replay so automation can distinguish it from normal catch-up.

### Q6. What exact acceptance examples should lock down local-day boundaries across DST changes—for example, a spring-forward day, a fall-back day, and a UTC-offset rollover?
### A6.
Test half-open UTC windows `[start, end)` with these fixed examples: `Europe/London` 2026-03-29 maps to `2026-03-29T00:00:00Z...2026-03-29T23:00:00Z` (23 hours); `Europe/London` 2026-10-25 maps to `2026-10-24T23:00:00Z...2026-10-26T00:00:00Z` (25 hours); and `Asia/Tokyo` 2026-01-15 maps to `2026-01-14T15:00:00Z...2026-01-15T15:00:00Z` (UTC-date rollover). In each case, a merge exactly at start is included and one exactly at end is excluded.

### Q7. For optional PR detail statistics, what should happen when one PR-detail request fails after search results were obtained: fail the whole day without advancing state, omit only that PR’s stats, or render a marked partial digest?
### A7.
Fail the whole day without sending or advancing state. When `line_stats: true`, complete statistics are part of that run's contract; silently omitting one PR or sending a partial digest would make totals misleading. Operators who prefer lower API cost or greater availability can disable `line_stats` in configuration and retry.

### Q8. What machine-readable result and exit-code distinctions must callers be able to rely on for success, dry-run, configuration refusal, GitHub failure, Telegram failure, and partial catch-up completion?
### A8.
Use exit `0` for a completed real run and for a successful dry-run, distinguished by JSON `status: "success"` versus `status: "dry_run"`; `2` for CLI/configuration refusal; `3` for GitHub fetch failure; `4` for Telegram delivery failure; `5` for state read/write failure; `6` for partial catch-up where at least one day was durably settled before a later day failed; and `1` for an unexpected internal error. JSON always includes `status`, `mode`, `requested_days`, `settled_days`, `skipped_days`, `failed_date`, `remaining_days`, and a redacted `error.kind/message` where applicable. Exit `6` retains the underlying failure kind in JSON.

### Q9. What concrete release-readiness evidence is required before v0.1.0 is considered complete—for example, supported Ruby versions, image smoke tests, systemd verification environment, gem build checks, and reviewer sign-off?
### A9.
Require: the offline suite green on Ruby 3.2, 3.3, and 3.4 with real network access blocked; gem build and clean install smoke tests for `version` and `run --dry-run`; a Docker build/run smoke as a non-root user using `Europe/London` and installed tzdata; `systemd-analyze verify` plus a clean Ubuntu VPS walkthrough of the oneshot, timer, state directory, and journald output; one manual authenticated validation of the GitHub merged-range query with no token or private payload in artifacts; one live Telegram smoke to an allowlisted test chat with token-redaction verification; README, security/scoping guidance, and changelog complete; and independent Codex and Grok review sign-off unless Grok explicitly reports its weekly limit. Build and prepare v0.1.0, but do not tag, publish the gem, or create a release without separate operator approval.

## Requirements
- **Actor:** A self-hosting operator runs PRDigest on a small VPS, using the existing Ruby gem scaffold or container image, explicit `owner/name` repositories and timezone in YAML, GitHub and Telegram tokens from environment variables, one allowlisted Telegram chat, and a systemd oneshot/timer.
- **Normal flow:** Each `prdigest run` computes owed local days from versioned durable state, applies the catch-up policy, processes retained days oldest-first, queries merged GitHub PRs for each half-open UTC day window, renders deterministic Telegram HTML, sends every chunk, and atomically advances state immediately after each settled day. Failures return a meaningful non-zero exit, remain visible in journald, and are retried from durable state on the next invocation.
- **Settled days:** Advance after all chunks are delivered, after an enabled empty-day message is delivered, after an empty day is intentionally suppressed, or after an over-cap historical day is explicitly skipped and reported. Any GitHub, rendering, Telegram, or state-write failure leaves the current day unsettled.
- **Partial delivery:** A day split across Telegram messages remains wholly unadvanced unless every chunk succeeds. Retry resends all chunks; v0.1.0 accepts possible duplicates rather than adding a per-chunk ledger.
- **Catch-up:** Default to 7 days, accept only `1..30`, retain the newest capped window, explicitly report and advance past older skipped days, then process retained days oldest-first.
- **Replay and dry-run:** `--date YYYY-MM-DD` is an explicit replay that bypasses state reads and writes, may resend an already delivered date, and is identified as a replay in JSON. Dry-run performs no Telegram send, does not read or write delivery progress, never advances state, and exposes no secrets.
- **GitHub details:** Search merged PRs per explicit repository and UTC window with pagination, retries, and mapped errors. When line statistics are enabled, any detail-fetch failure fails the whole day before sending or advancing; operators may disable statistics to reduce API cost and availability risk.
- **Rendering and delivery:** Preserve configuration-order grouping, totals/footer, empty-day behavior, hostile-title escaping, Telegram HTML parse mode, 4096-character section-aware splitting, sender-level allowlist refusal, 429 `retry_after` handling, pacing, and token-redacted errors.
- **Configuration:** Resolve config from `PRDIGEST_CONFIG`, then `/etc/prdigest/config.yml` when present, otherwise require `--config`. Tokens remain environment-only and must never appear in logs, human output, JSON, fixtures, or other artifacts.
- **Results and exits:** JSON always includes `status`, `mode`, `requested_days`, `settled_days`, `skipped_days`, `failed_date`, `remaining_days`, and redacted `error.kind/message` when applicable. Exit codes are `0` completed real run or successful dry-run, `2` CLI/config refusal, `3` GitHub failure, `4` Telegram failure, `5` state failure, `6` partial catch-up after at least one durable settlement, and `1` unexpected internal error; JSON distinguishes `success`, `dry_run`, replay mode, and the underlying partial-failure kind.
- **Acceptance examples:** `Europe/London` 2026-03-29 maps to `[2026-03-29T00:00:00Z, 2026-03-29T23:00:00Z)` (23 hours); 2026-10-25 maps to `[2026-10-24T23:00:00Z, 2026-10-26T00:00:00Z)` (25 hours); `Asia/Tokyo` 2026-01-15 maps to `[2026-01-14T15:00:00Z, 2026-01-15T15:00:00Z)`. A merge exactly at the start is included and one exactly at the end is excluded.
- **Release evidence:** The offline suite passes with real network access blocked on Ruby 3.2, 3.3, and 3.4; gem build and clean-install smoke tests cover `version` and `run --dry-run`; the Alpine image runs as non-root with tzdata; systemd units pass `systemd-analyze verify` and a clean Ubuntu VPS walkthrough; authenticated GitHub query and allowlisted Telegram smokes leave no credentials or private payloads in artifacts; documentation covers operations and credential scoping; changelog and v0.1.0 packaging are ready.
- **Scope and approval:** Implement M1 through M6 in order while preserving scaffold compatibility except for the safe config-path change. Exclude Hive integration, a web UI, non-GitHub forges, multi-chat routing, and long-running scheduling. Require independent Codex and Grok review sign-off unless Grok explicitly reports its weekly limit. Prepare v0.1.0 without tagging, publishing, or creating a release until an operator explicitly approves it.
